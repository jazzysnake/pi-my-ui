pi-my-ui — design variants

Three deliberately different visual directions for the mobile UI, rendered as plain static HTML. Not shipped code — a way to react to layout and density before any Svelte is written.

Open a variant below, then fill in CHOICES.md (one row per surface). View by opening these files directly with file://, or run python3 -m http.server from the repo root and browse to docs/design/. See README.md for scope.

Chosen direction (2026-10-11): A — “Console” as the base — A's blue/cyan-led palette and A's dense monospace-led type — with C's composer-control geometry (a 44×44 round send/stop and a 44×44 square branch button, branch rightmost), restyled into A. B is rejected — borrow nothing. Recorded verbatim in USER-FEEDBACK.md and decided in ADR 0017.

A — “Console”chosen base

Keep the terminal lineage: one dense monospace stream where every surface is a compact hairline row and the transcript is the interface.

Optimises for density and fast scanning · Trades away touch comfort and glance-level separation — open →

B — “Journal”rejected

Treat the conversation as a calm timeline: each turn is a distinct card on a rail, with generous spacing and one clear thing to read at a time.

Optimises for reading comfort and glanceability · Trades away density — far fewer messages per screen, more scrolling — open →

C — “Focus”composer geometry adopted

Strip the chrome: the transcript is plain type on near-black, and every secondary surface is a sheet you pull up, not a thing that lives on screen.

Optimises for one-handed reach and an immersive read · Trades away at-a-glance status and discoverability — open →

Every variant covers the same surfaces required by ADR 0012 and the E3 tickets: transcript, composer, sidebar, agent pill and list, /tree, the / palette, !/!! bash cards, and the errored / aborted / compacting run states. The variants differ only in layout, hierarchy, density and navigation.
